# Git Commit Message 决策流程

本文档详细说明了生成 commit message 时的分析流程、判断规则和特殊场景处理。

## 核心决策流程

### 0. 分析范围判断流程（新增，第一步）

```
用户输入分析
  ↓
判断用户是否指定分支？
  ├─ 是 → [分支对比模式]
  │     ├─ 运行: git diff <target-branch> --name-only
  │     ├─ 运行: git diff <target-branch>
  │     └─ 获取所有变更文件和具体改动内容
  │
  └─ 否 → [默认模式]
        ├─ 检查暂存区（git diff --staged --name-only）
        │     ├─ 有暂存文件 → [暂存区模式]
        │     │     ├─ 运行: git diff --staged
        │     │     └─ 分析暂存的改动内容
        │     │
        │     └─ 无暂存文件 → [未提交文件模式]
        │           ├─ 运行: git diff --name-only
        │           ├─ 运行: git diff
        │           └─ 分析未提交的改动内容
        │
        └─ 收集用户提供的上下文和意图说明
```

### 1. 信息收集流程（基于分析范围）

**暂存区模式**：
```
运行 git status → 确认暂存状态
运行 git diff --staged --name-only → 获取变更文件列表
运行 git diff --staged → 分析具体改动内容
识别文件类型和路径
```

**未提交文件模式**：
```
运行 git status → 确认工作区状态
运行 git diff --name-only → 获取变更文件列表
运行 git diff → 分析具体改动内容
识别文件类型和路径
```

**分支对比模式**：
```
运行 git status → 确认当前分支
运行 git diff <target-branch> --name-only → 获取变更文件列表
运行 git diff <target-branch> → 分析具体改动内容
识别文件类型和路径
识别变更涉及的 commit 数量和历史
```

**共同步骤**：
```
收集用户提供的上下文说明和改动意图
统计改动规模（文件数量、行数变化）
识别改动的关键特征
```

### 2. 类型判断流程

```
分析改动内容 → 判断核心意图
  ↓
[新增功能特征]
  ├─ 新增函数/方法/接口 → feat
  ├─ 实现新功能模块 → feat
  └─ 添加新的 SKILL → feat
  ↓
[修复错误特征]
  ├─ 修复逻辑错误 → fix
  ├─ 修复崩溃问题 → fix
  ├─ 修复性能问题 → fix 或 perf（视影响程度）
  └─ 修复安全漏洞 → fix
  ↓
[文档更新特征]
  ├─ 修改 .md 文件 → docs
  ├─ 更新文档内容 → docs
  └─ 添加文档说明 → docs
  ↓
[代码格式特征]
  ├─ 仅修改缩进/空格 → style
  ├─ 调整代码格式 → style
  └─ 统一代码风格 → style
  ↓
[重构特征]
  ├─ 修改代码结构但功能不变 → refactor
  ├─ 提取公共方法 → refactor
  ├─ 重新组织模块 → refactor
  └─ 优化设计模式 → refactor
  ↓
[性能优化特征]
  ├─ 优化查询性能 → perf
  ├─ 优化算法 → perf
  └─ 优化资源使用 → perf
  ↓
[测试变更特征]
  ├─ 修改测试文件 → test
  ├─ 添加测试用例 → test
  └─ 修复测试逻辑 → test
  ↓
[构建相关特征]
  ├─ 修改 Makefile → build
  ├─ 修改 go.mod → build
  ├─ 修改 Dockerfile → build
  └─ 升级依赖版本 → build
  ↓
[CI 相关特征]
  ├─ 修改 GitHub Actions → ci
  ├─ 修改 GitLab CI → ci
  └─ 修改 CI 配置 → ci
  ↓
[其他维护性工作]
  ├─ 修改 .gitignore → chore
  ├─ 添加配置文件 → chore
  └─ 其他不修改代码的工作 → chore
  ↓
[回退操作]
  └─ Revert 之前的 commit → revert
  ↓
验证类型选择 → 确定最终类型
```

### 3. 范围判断流程

```
分析改动路径 → 判断影响范围
  ↓
[单一模块/目录 → 使用路径范围]
  ├─ .claude/skills/* → .claude/skills/<skill-name>
  ├─ internal/biz/* → internal/biz
  ├─ internal/data/* → internal/data
  ├─ internal/service/* → internal/service
  └─ api/helloworld/v1/* → api/helloworld/v1
  ↓
[跨多个模块 → 使用标准范围]
  ├─ cmd/web/* → web
  ├─ cmd/task/* → task
  ├─ api/* → api
  ├─ internal/* → internal
  ├─ docs/* → docs
  └─ 配置/工具/脚本 → build/ci/chore
  ↓
[特殊情况]
  ├─ 全局性改动 → 不使用范围
  ├─ 配置性改动 → build 或 ci
  └─ 多个改动范围 → 选择最主要或最上层
  ↓
验证范围选择 → 确定最终范围
```

### 4. 描述提炼流程

```
理解改动核心意图 → 识别关键动作
  ├─ 新增: 添加、新增、引入、实现、集成
  ├─ 修复: 修复、修正、解决、处理
  ├─ 更新: 更新、升级、优化、改进
  ├─ 重构: 重构、调整、改进、优化
  └─ 删除: 删除、移除、废弃
  ↓
识别影响对象
  ├─ 功能模块: 用户管理、权限控制、数据统计、缓存策略
  ├─ 技术组件: 中间件、数据库连接、日志管理、配置管理
  ├─ 文档类型: API 文档、使用说明、设计文档、调研文档
  └─ 配置项: 日志级别、超时时间、连接池大小
  ↓
组合动宾结构
  ├─ 动词 + 对象: "添加用户管理功能"
  ├─ 动词 + 对象 + 目的: "重构业务层以提升可维护性"
  └─ 动词 + 对象 + 方式: "优化数据库查询性能"
  ↓
检查语言规范
  ├─ 是否祈使句？
  ├─ 首字母是否小写？
  ├─ 是否使用"了"？（应避免)
  ├─ 结尾是否有句号？（应避免)
  ├─ 是否口语化？（应避免）
  └─ 长度是否在 50 字以内？
  ↓
提炼最终描述
```

### 5. 四层验证流程（严格模式）

```
第一层：格式验证
  ├─ 检查: <类型>(<范围>): <描述>
  ├─ 验证: 正则表达式匹配
  ├─ 通过 → 进入第二层
  └─ 不通过 → 调整格式并重新验证
  ↓
第二层：类型-范围一致性验证
  ├─ 检查类型与范围是否匹配
  ├─ 参考: 类型-范围映射表
  ├─ 通过 → 进入第三层
  └─ 不通过 → 调整范围并重新验证
  ↓
第三层：语言和语法验证
  ├─ 检查: 中文表述规范性
  ├─ 检查: 语法正确性
  ├─ 检查: 是否口语化
  ├─ 通过 → 进入第四层
  └─ 不通过 → 优化表述并重新验证
  ↓
第四层：代码改动一致性验证
  ├─ 对比 git diff 内容
  ├─ 验证: message 与改动是否一致
  ├─ 检查: 是否遗漏重要信息
  ├─ 通过 → 输出最终 message
  └─ 不通过 → 完善描述并重新验证
```

## 特殊场景决策

### 多类型改动处理

```
识别主要改动类型
  ├─ 70% 以上为一种类型 → 使用该类型
  ├─ 功能为主，修复为辅 → 拆分提交（feat + fix）
  ├─ 重构为主，新功能为辅 → 拆分提交（refactor + feat）
  └─ 无法明确区分 → chore (需在描述中详细说明)
```

### 跨范围改动处理

```
分析改动涉及的模块
  ├─ 单一职责改动 → 选择最直接的范围
  ├─ 跨层改动 → 选择最上层的范围
  ├─ 全局性改动 → 不使用范围
  └─ 配置性改动 → build 或 ci
```

### 重构性修复处理

```
判断改动本质
  ├─ 主要是修复 bug → fix
  ├─ 主要是改进设计 → refactor
  ├─ 修复 + 轻微重构 → fix (在描述中说明)
  └─ 重构 + 顺便修复 → refactor (在描述中说明)
```

### 分支对比模式的特殊处理

```
分支对比场景
  ├─ 单一 commit: 生成标准 commit message
  ├─ 多个 commit: 生成综合 commit message 或拆分建议
  ├─ 合并多个功能: 建议生成多个 commit message
  └─ 大型重构: 生成总体描述 + 建议拆分
```

## 决策原则

### 1. 类型选择优先级

```
新功能 > 重构 > 修复 > 其他
```

**说明**：
- 如果同时包含新功能和重构，优先判断主要意图
- 如果重构为主但包含新功能，使用 refactor
- 如果新功能为主但包含重构，使用 feat

### 2. 范围选择优先级

```
路径范围 > 标准范围 > 无范围
```

**说明**：
- 优先使用具体的路径范围（更精确）
- 如果跨多个模块，使用标准范围
- 如果全局性改动，不使用范围

### 3. 描述提炼原则

```
动宾结构 > 目的描述 > 简单描述
```

**说明**：
- 优先使用"动作 + 对象"结构
- 需要时添加目的说明
- 避免过于简单或过于复杂

## 常见决策错误

### 错误 1：类型判断失误

```
❌ fix(data): 添加新的查询方法  # 应该是 feat
❌ feat: 修复数据库连接问题  # 应该是 fix
```

### 错误 2：范围选择不当

```
❌ feat: 添加用户功能  # 缺少范围
❌ feat(Api): 添加接口  # 范围首字母大写
❌ test(api): 添加接口测试  # 类型-范围不匹配
```

### 错误 3：描述不符合规范

```
❌ feat: 添加了用户管理功能  # 使用"了"
❌ feat: 添加用户功能。  # 结尾有句号
❌ fix: 修复数据库的问题  # "的"字冗余
```

### 错误 4：忽略特殊场景

```
❌ 多个功能混合：feat: 添加功能和修复错误  # 应该拆分
❌ 跨层改动：feat(web): 添加功能（实际包含 web 和 task）  # 应该用全局
❌ 重构性修复：fix: 重构用户权限验证  # 应该根据主要意图判断
```

## 决策检查清单

在最终确定 commit message 前，检查以下问题：

### 类型检查

- [ ] 类型是否在 11 种预定义类型中？
- [ ] 类型是否准确反映改动本质？
- [ ] 是否优先级判断正确（新功能 > 重构 > 修复）？

### 范围检查

- [ ] 范围是否准确指向改动的模块？
- [ ] 是否优先使用路径范围？
- [ ] 类型-范围是否匹配（参考映射表）？

### 描述检查

- [ ] 是否使用祈使句？
- [ ] 是否首字母小写？
- [ ] 是否结尾无句号？
- [ ] 是否避免口语化？
- [ ] 是否在 50 字以内？
- [ ] 是否简洁明了？

### 一致性检查

- [ ] message 与实际改动是否一致？
- [ ] 是否遗漏重要信息？

通过以上检查，可以确保生成的 commit message 符合项目规范，并且准确描述了代码改动。
