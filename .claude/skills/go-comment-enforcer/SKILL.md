# Go 代码注释规范检查器

## 概述

`go-comment-enforcer` 是一个纯 Claude 驱动的 Go 代码注释规范检查与修复 SKILL,无需任何脚本,仅通过 Claude 智能分析代码实现注释规范检查、修复和建议。

**核心特性**:
- 📊 **四种工作模式**: 检查报告、直接修复、生成建议、符合度评分
- 🎯 **智能分析**: Claude 深度理解代码语义,准确识别注释问题
- 🔒 **安全可靠**: 使用临时文件夹备份,不操作 git,自动验证修改
- ⚡️ **容错优先**: 部分文件失败不影响整体,清晰展示无法处理的文件

## 使用场景

- **代码审查前检查**: 生成注释规范检查报告,识别潜在问题
- **注释规范化**: 自动修复注释问题,统一项目注释风格
- **代码质量评估**: 评估注释规范符合度,生成改进路线图
- **注释生成**: 为缺失注释的代码提供规范的注释建议

**默认范围** (排除生成代码和测试):
- `internal/` - 内部实现
- `cmd/` - 应用入口
- `pkg/` - 公共包 (如果存在)

**自定义范围**:

- 包含测试文件: "包含测试文件一起检查"
- 指定目录: "只检查 internal/biz/ 和 internal/data/"

#### 步骤 2: 执行检查或修复

根据你的需求,选择对应的工作模式 (详见下方"工作模式"章节)

- **检查报告**: 查看问题列表,优先级排序
- **直接修复**: 审查修复预览,确认后执行
- **生成建议**: 选择性地应用注释建议
- **符合度评分**: 查看得分和改进路线图

## 工作模式

### 模式 1: 检查报告

**使用场景**: 代码审查前检查、定期代码质量检查

**用户触发词**:
- "检查注释"
- "注释规范检查"
- "分析注释问题"

**Claude 行为**:
1. 扫描 Go 文件 (根据用户意图决定是否排除生成代码)
2. 检查注释完整性、一致性、质量
3. 生成 Markdown 格式的问题报告
4. **不修改任何代码**

**输出内容**:
- 📊 总览统计 (文件数、问题数、分类统计)
- 📋 详细问题列表 (按严重程度排序)
- 🔍 每个问题包含: 文件位置、问题描述、当前代码、建议代码
- ⭐ 修复优先级建议
- ⚠️ 无法处理的文件 (如果有)

### 模式 2: 直接修复

**使用场景**: 注释规范化、批量修复注释问题

**用户触发词**:
- "修复注释"
- "检查并修复注释"
- "fix comments"

**Claude 行为**:
1. 先执行模式 1 的检查流程
2. 生成问题报告
3. **创建临时备份目录**: `.claude/temp/comment-backup-[timestamp]/`
4. **展示修复预览** (逐文件展示将要修改的内容)
5. **等待用户确认**
6. 用户确认后,使用 Edit 工具直接修复代码
7. 运行 `go build ./...` 和 `make lint` 验证
8. 验证失败则从临时备份恢复
9. 生成修复对比报告
10. **自动清理临时备份目录**

**修复原则**:
- 包注释: 创建 doc.go 文件,删除其他文件中的包注释
- 类型注释: 添加缺失的类型和字段注释
- 接口一致性: 修改实现方法注释,使其与接口定义完全一致
- 函数注释: 补充完整的参数和返回值说明
- 格式问题: 添加缺失的标点符号

**输出内容**:
- 📋 修复预览 (修改前后对比)
- ✅ 修复完成报告
- ⚠️ 修改失败的文件 (如果有)
- 🔍 验证结果 (go build, make lint)

### 模式 3: 生成建议

**使用场景**: 代码补全注释、学习注释规范

**用户触发词**:
- "生成注释建议"
- "注释缺失建议"
- "为我生成注释"

**Claude 行为**:
1. 识别所有缺失的注释
2. 分析代码上下文 (变量名、函数逻辑、类型用途)
3. 为每个缺失点生成符合规范的注释建议
4. 输出结构化的建议列表
5. **不直接修改代码**

**输出内容**:
- 📝 按文件组织的建议列表
- 💡 每个建议包含: 位置信息、建议注释代码、生成理由
- 🔗 应用方式说明 (全部应用 / 选择应用 / 审查后应用)
- ⚠️ 无法处理的文件 (如果有)

### 模式 4: 符合度评分

**使用场景**: 代码质量评估、改进规划

**用户触发词**:
- "评分"
- "注释质量评分"
- "规范符合度"

**Claude 行为**:
1. 检查所有注释规范点
2. 计算符合度得分 (0-100 分)
3. 生成评分卡
4. 提供改进路线图

**评分维度**:
1. 包注释规范 (权重 15%)
2. 类型注释规范 (权重 25%)
3. 函数注释规范 (权重 30%)
4. 接口一致性 (权重 15%)
5. 格式规范 (权重 15%)

**输出内容**:
- 🎯 总体得分和等级 (优秀/良好/及格/不及格)
- 📊 分维度详细评分
- 📈 改进路线图 (分阶段,含目标得分和具体措施)

## 核心检查点

### 完整性检查

1. **包级别注释**
   - 每个包是否有独立的 doc.go 文件
   - doc.go 格式是否正确 (版权声明 + 包注释 + package)
   - 非 doc.go 文件是否包含包注释 (违反规范)

2. **类型注释完整性**
   - 接口是否有功能说明
   - 结构体是否有用途说明
   - 字段是否有用途说明

3. **函数注释完整性**
   - 是否有功能说明
   - 参数说明是否完整
   - 返回值说明是否完整

4. **全局变量注释完整性**
   - 是否有用途说明
   - 注释是否避免冗余地重复变量名
   - 是否说明变量的设计模式（如单例、常量等）

5. **错误变量注释完整性**
   - 是否说明错误类型和错误原因
   - 是否提供使用场景示例
   - 是否说明何时返回该错误

### 接口一致性检查

- 实现方法的注释是否与接口定义完全一致
- 参数和返回值说明是否逐字相同
- 如果接口定义缺少注释,先生成接口注释

### 语义质量检查

- 注释是否准确反映代码功能
- 是否使用技术领域专业术语
- 是否有口语化表达
- 是否有说明性 (而非重复代码)
- **全局变量注释是否避免冗余**：不要写"logger 是日志记录器"这类重复变量名的注释，应直接说明用途和设计模式
- **错误变量注释是否准确**：不要把错误变量当成错误消息来注释，应说明错误类型、返回场景和使用方式

### 格式规范检查

- 注释是否以中文标点结束
- 是否使用标准术语表
- 注释位置是否正确

## 注释详细程度控制

### 概述

`go-comment-enforcer` 支持根据用户需求生成不同详细程度的函数体内注释。

**默认行为**: 如果用户未指定详细程度,使用**标准版本**。

### 详细程度级别

#### 级别 1: 简洁版本 (minimal)

**特征**:
- 仅注释关键业务逻辑和重要判断
- 不注释显而易见的代码
- 适合经验丰富的开发团队

**用户触发词**:
- "简洁注释"
- "minimal comments"
- "最简注释"

**示例**:
```go
// CreateGreeter 创建一个新的 Greeter 实体。
//
// 参数：
//   - ctx: 请求上下文,用于取消与超时控制。
//   - g: 待创建的 Greeter 实体,Hello 字段不能为空。
//
// 返回：
//   - *Greeter: 创建成功的实体,包含生成的标识。
//   - error: Hello 字段为空时返回错误,成功时返回 nil。
func (u *greeterUsecase) CreateGreeter(ctx context.Context, g *Greeter) (*Greeter, error) {
    if "" == g.Hello {
        return nil, fmt.Errorf("Hello 字段不能为空")
    }

    greeter, err := u.repo.Save(ctx, g)
    if nil != err {
        return nil, fmt.Errorf("保存数据失败: %w", err)
    }

    return greeter, nil
}
```

#### 级别 2: 标准版本 (standard) - **默认**

**特征**:
- 注释复杂业务逻辑的原因
- 注释关键步骤的目的
- 平衡详细度和可读性
- 适合大多数开发场景

**示例**: 参见 [function_comment_rules.md](references/function_comment_rules.md#函数体内注释规范) 中的示例

#### 级别 3: 详细版本 (detailed)

**特征**:
- 注释每个逻辑块的目的
- 解释算法步骤和数据流
- 注释错误处理和边界条件
- 适合学习代码和代码审查

**用户触发词**:
- "详细注释"
- "detailed comments"
- "详细版注释"
- "教育注释"

**示例**:
```go
// CreateGreeter 创建一个新的 Greeter 实体。
//
// 参数：
//   - ctx: 请求上下文,用于取消与超时控制。
//   - g: 待创建的 Greeter 实体,Hello 字段不能为空。
//
// 返回：
//   - *Greeter: 创建成功的实体,包含生成的标识。
//   - error: Hello 字段为空时返回错误,成功时返回 nil。
func (u *greeterUsecase) CreateGreeter(ctx context.Context, g *Greeter) (*Greeter, error) {
    // 第一步: 验证输入数据的完整性和有效性。
    // 这是业务层面的规则,确保不会创建无效实体。
    if "" == g.Hello {
        return nil, fmt.Errorf("Hello 字段不能为空")
    }

    // 第二步: 调用仓储层持久化数据到数据库。
    // 仓储层负责具体的数据库操作,业务层不直接访问数据库。
    greeter, err := u.repo.Save(ctx, g)
    if nil != err {
        // 保存失败时,使用 fmt.Errorf 包装错误,保持错误链。
        return nil, fmt.Errorf("保存数据失败: %w", err)
    }

    // 第三步: 返回创建成功的实体,包含数据库生成的 ID。
    return greeter, nil
}
```

#### 级别 4: 教育版本 (educational)

**特征**:
- 逐行解释代码逻辑
- 说明为什么这样写而不是那样写
- 包含最佳实践和设计模式说明
- 适合教学和新人培训

**用户触发词**:
- "教育注释"
- "educational comments"
- "教学注释"
- "逐行注释"

**示例**:
```go
// CreateGreeter 创建一个新的 Greeter 实体。
//
// 参数：
//   - ctx: 请求上下文,用于取消与超时控制。
//   - g: 待创建的 Greeter 实体,Hello 字段不能为空。
//
// 返回：
//   - *Greeter: 创建成功的实体,包含生成的标识。
//   - error: Hello 字段为空时返回错误,成功时返回 nil。
func (u *greeterUsecase) CreateGreeter(ctx context.Context, g *Greeter) (*Greeter, error) {
    // 验证输入: 在进行任何操作之前,先验证数据的有效性。
    // 这样可以尽早发现错误,避免无效数据进入系统。
    if "" == g.Hello {
        // 返回错误而不是 panic,这是 Go 的错误处理最佳实践。
        return nil, fmt.Errorf("Hello 字段不能为空")
    }

    // 调用仓储层: 通过接口调用数据访问层,而不是直接访问数据库。
    // 这遵循了依赖倒置原则,使代码更易于测试和维护。
    greeter, err := u.repo.Save(ctx, g)
    if nil != err {
        // 错误包装: 使用 %w 包装错误,保留原始错误信息。
        // 这样调用者可以追溯到根本原因。
        return nil, fmt.Errorf("保存数据失败: %w", err)
    }

    // 返回结果: 返回包含完整信息的实体,包括数据库生成的 ID。
    // 这样调用者可以使用返回的实体继续后续操作。
    return greeter, nil
}
```

## Claude 智能分析流程

### 文件收集策略

**重要原则**: 生成代码的排除策略由用户的提示词决定,不在 SKILL 中硬编码。

**Glob 模式** (默认):
```go
// 主代码(手写)。
"**/*.go"

// 排除生成代码(默认,但用户可覆盖)。
"!**/*.pb.go"
"!**/wire_gen.go"
"!**/*.gen.go"
"!**/mock_*.go"
"!**/*.mock.go"

// 排除测试文件(默认,但用户可覆盖)。
"!**/*_test.go"
```

**用户意图识别**:
- 用户说 "检查所有代码" → 包含生成代码
- 用户说 "检查手写代码" → 排除生成代码 (默认)
- 用户说 "包含测试文件" → 包含测试文件
- 用户说 "包含 *.pb.go" → 包含特定生成代码

### 信息提取策略

**关键代码元素识别** (Claude 智能分析):

1. **包级别**
   - 检查是否存在 `doc.go` 文件
   - 检查非 `doc.go` 文件中是否有包注释
   - 验证 `doc.go` 格式 (版权声明 + 包注释 + package)

2. **接口定义**
   - 提取接口类型声明
   - 提取每个方法的注释
   - 记录参数名、类型和注释
   - 记录返回值类型和注释

3. **实现方法**
   - 查找实现接口的方法
   - 提取方法注释
   - 与接口定义逐字比对

4. **类型声明**
   - 提取结构体字段
   - 检查字段注释
   - 检查类型注释

5. **函数声明**
   - 提取函数名、参数、返回值
   - 检查函数注释
   - 验证参数和返回值注释

6. **标准术语**
   - 识别 `context.Context` 参数
   - 识别 `*Config` 参数
   - 识别 `Logger` 参数
   - 验证注释是否使用标准表述

### 失败处理策略

**核心原则**: 先处理可处理的文件,列举不可处理的文件给用户核对,避免卡住。

**重试策略**:
- 每个文件最多尝试 3 次
- 第 3 次失败后,标记为 "无法处理"
- 继续处理其他文件
- 在报告中单独列出 "⚠️ 无法处理的文件"

### 验证和回滚策略

**备份策略**:
```bash
# 创建临时备份目录
TEMP_BACKUP_DIR=".claude/temp/comment-backup-$(date +%s)"
mkdir -p "$TEMP_BACKUP_DIR"

# 备份文件
cp path/to/file.go "$TEMP_BACKUP_DIR/"

# 全部事务结束后清理
rm -rf ".claude/temp/comment-backup-*"
```

**验证流程**:
1. 修复完成后,自动运行 `go build ./...` 验证语法
2. 自动运行 `make lint` 验证功能正常
3. 如果验证失败,从临时备份恢复并记录到 "修改失败的文件"
4. 在报告中列出所有验证结果
5. 全部成功后,自动清理临时备份目录

## 全局变量和错误变量注释规范

### 全局变量注释

**基本原则**：避免冗余，直接说明用途和设计模式。

**正确示例**：
```go
// ProviderSet 是业务层的依赖注入提供者集合。
var ProviderSet = wire.NewSet(NewGreeterUsecase)

// logger 使用单例模式的全局日志记录器实例，确保整个应用程序使用同一个日志记录器。
var logger kitlog.Logger
```

**错误示例**：
```go
// ProviderSet 提供者集合。（❌ 过于简略）
var ProviderSet = wire.NewSet(NewGreeterUsecase)

// logger 是全局共享的日志记录器实例。（❌ 冗余，重复了变量名"logger"）
var logger kitlog.Logger
```

### 错误变量注释

**基本原则**：说明错误类型、错误原因、返回场景，而不是简单描述错误消息。

**正确示例**：
```go
// ErrUserNotFound 表示用户未找到的错误，使用 NotFound 错误类型，错误原因为 USER_NOT_FOUND。
var ErrUserNotFound = errors.NotFound(
```

### 修复原则

**全局变量**：
- 避免写"X 是Y"这种冗余注释
- 直接说明用途："X 使用Y设计模式的Z"
- 如果是常量，说明为什么是常量
- 如果是单例，说明单例模式的目的

**错误变量**：
- 必须说明错误类型（NotFound、InvalidArgument 等）
- 必须说明错误原因或错误码
- 应该提供使用场景示例（何时检查此错误）
- 对于复杂错误，说明在哪些情况下返回此错误

4. **迭代改进**: 重复检查-修复-验证循环,直到符合要求

### 修复后处理

1. **审查修复报告**: 检查所有修改是否正确
2. **运行测试**: 确保 `make test` 通过
3. **提交代码**: 创建分支提交注释改进
4. **更新文档**: 如果有新的标准术语,更新 [terminology_table.md](references/terminology_table.md)

## 故障排除

### 常见问题

#### 问题 1: Claude 无法理解代码结构

**症状**: 某些文件被标记为 "无法处理"

**原因**: 代码使用了复杂的泛型或宏

**解决方案**:
- 手动审查这些文件的注释
- 参考 [function_comment_rules.md](references/function_comment_rules.md) 手动添加注释
- 简化代码结构（如果可能）

#### 问题 2: 验证失败导致修改被回滚

**症状**: 某些文件修改后被标记为 "修改失败"

**原因**: 注释修改可能影响了代码结构（如意外删除了重要的包注释）

**解决方案**:
- 查看验证失败的错误信息
- 手动修复该文件的注释
- 确保不要删除非 doc.go 文件中的版权声明

#### 问题 3: 生成的注释不符合实际功能

**症状**: 注释内容与代码实际功能不匹配

**原因**: Claude 误解了代码的业务含义

**解决方案**:
- 在回复中提供更多上下文信息
- 参考代码的其他部分（如测试文件）理解功能
- 手动调整生成的注释

### 回滚操作

**全部回滚**:
```bash
# 从临时备份恢复所有文件
cp -r ".claude/temp/comment-backup-XXX/"* "./"
```

**部分回滚**:
```bash
# 只恢复特定文件
cp ".claude/temp/comment-backup-XXX/file.go" "path/to/file.go"
```

**清理临时文件**:
```bash
# 清理所有备份目录
rm -rf ".claude/temp/comment-backup-*"
```
